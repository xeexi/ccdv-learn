5-11　プロンプトキャッシュ ─ 同じ前半を安く使い回す

ゴールキャッシュが効く並べ方と、区切りの置き場所を選べる。

アプリ→Claude

長い指示や資料を毎回送っているなら、その前半をキャッシュに置けます。2回目からは、置いた部分を読み出すだけになり、安く、速く処理されます。

DOMAIN 5Cost and Token Management　／　DOMAIN 2Claude API Mechanics

効くのは「前半の一致」だけ

ゴールキャッシュが外れる原因を、並び順から説明できる。

API は、ツールの定義、system、会話の順にプロンプトを並べて処理します。キャッシュは先頭から一致している部分にしか効きません。だから変わらないものを前に、変わるものを後ろに置きます。

黙って外す原因何が起きるか
先頭に日時system の先頭に日時を埋め込むと、毎回先頭が変わり、何も読み出されない
並びが揺れるツールの並びや JSON のキーの順が毎回変わると、見た目は同じでも別物として扱われる
モデルを替えるキャッシュはモデルごとに別なので、替えた先では使えない

区切りをどこに置くか

ゴール共通部分の終わりに区切りを置く理由を言える。

キャッシュしたい範囲の、終わりのブロックに cache_control を付けます。これがキャッシュの区切り（cache check-pointing）で、1回のリクエストに4つまで置けます。

"system": [{ "type": "text", "text": "（長い指示）",
             "cache_control": { "type": "ephemeral" } }]
使い方区切りの置き場所
共通の長い指示system の最後。多くのリクエストが同じ指示を読み出す
共通の資料 ＋ 毎回違う質問共通部分の終わり（質問の手前）
会話を続ける最新の発言の最後。前回までの区切りも、読み出し口として残る

会話を続ける使い方なら、リクエストの外側に cache_control を1つ付けるだけで、最後のブロックに自動で置かれます。

誤解「区切りは末尾に置けば、全部キャッシュされて得」 実際は毎回違う質問まで含めると、毎回別のものとして書き込まれ、読み出しが起きない。書き込みの割増だけを払うことになる。

寿命と、割増・割引

ゴールキャッシュが得になる条件と、効いているかの確かめ方を言える。

置いたキャッシュは既定で5分残り、読み出されるたびに延びます。間が空くなら、1時間の指定もできます。書き込みは通常の入力より割高、読み出しは大幅に割安なので、同じ前半を繰り返し使うほど得になります。一度しか使わない部分に区切りを置くと、割増だけを払います。

短すぎる前半は、区切りを付けても黙ってキャッシュされません（最小の長さはモデルで決まります）。効いているかは、応答の使用量の cache_read_input_tokens で確かめます。繰り返し送っているのに 0 のままなら、どこかで前半が変わっています。

ポイント変わらないものを前に、変わるものを後ろに並べ、共通部分の終わりに区切りを置く。効いているかは推測せず、使用量で確かめる。
