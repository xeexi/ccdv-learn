5-2　コンテキストウィンドウ ─ 入力と出力が同じ枠を使う

ゴール会話が長くなると何が起きるかを、窓の大きさと送り直しから説明できる。

アプリ→Claude

モデルが一度に扱えるトークンの量には上限があります。これが窓（context window）で、入力と出力の両方がこの1つの枠に入ります。

DOMAIN 5LLM Fundamentals

ポイントAPI は会話を覚えていない。続きを話すには、アプリが毎回それまでの履歴を全部送る。だから往復するほど、1回の入力が膨らむ。

入力と出力が、同じ枠を食い合う

ゴール窓に入るものを挙げ、長い会話で起きることと打つ手を言える。

窓に入るのは、指示（system）・ツールの定義・これまでの会話・今回の入力と、これから書く出力（考えた分を含む）です。入力が大きいほど、出力に使える残りは減ります。

起きることどこで分かるか打つ手
入力だけで窓を超えるリクエストがエラーで返る古い部分を刈り込む・要約する（〈窓を守る〉）
出力が途中で打ち切られる応答の stop_reason が、上限に達したことを示す出力の上限を見直す・入力を減らす
往復のたびに遅く、高くなる使用量のトークン数が、回ごとに増える同じ前半を使い回す（〈プロンプトキャッシュ〉）
誤解「窓の大きいモデルなら、何でも全部入れておけばよい」 実際は入れた分だけ毎回の費用と待ち時間がかかる。関係のないものまで入れると、必要な情報も埋もれやすい。

※ 窓の大きさはモデルで決まり、世代で変わるので、この教材には数値を書きません。実際の値は、公式のモデル一覧か Models API の max_input_tokens で確かめます。
