4-1　エラーの種類と、立て直し方

ゴールエラーを種類で見分け、再試行するか直すかを選べる。

Claude→アプリ

Claude のアプリの失敗は、大きく3つに分かれます。API が HTTP のエラーを返すもの、成功（200）で返ったのに途中で止まっているもの、形は正しいのに中身が違うものです。種類ごとに、再試行するか、直すか、別の手に回すかが決まります。

DOMAIN 4Debugging and Error Handling

状態種類次の手
400invalid_request_errorリクエストの形の誤り。直してから送る
401authentication_error鍵が無いか、正しくない。鍵を確かめる
402billing_error請求や支払いの問題。支払いの情報を確かめる
403permission_errorその鍵には許されていない。権限を確かめる
404not_found_error宛先やモデルの ID を確かめる
409conflict_error相手の今の状態とぶつかった。ぶつかりを解いてから再試行する
413request_too_large大きすぎる。中身を減らすか分ける
429rate_limit_error送りすぎ。間を空けて再試行する。ただし月の支出の上限に達したときは retry-after が付かず、待っても通らない
500api_error受けた側の不調。間を空けて再試行する
504timeout_error処理の途中で時間切れ。長い処理は逐次（ストリーミング）で受ける
529overloaded_error混雑。間を空けて再試行する

ポイント再試行してよいのは、混雑や受けた側の不調が原因のもの（429・5xx・接続の切断）。4xx の多くは、同じ内容で送り直しても通らない。

200 で返る失敗

ゴールHTTP では成功なのに、仕事としては失敗している応答を見分けられる。

止まった理由起きていること次の手
max_tokens上限で切れた上限を上げるか、続きを頼む。そのまま使わない
refusal安全のために断った同じモデルに送り直しても、たいてい断られる。stop_details で断った分野を見て、別のモデルで送り直すか人に回し、記録する
model_context_window_exceeded書く途中で窓の端に届いた切れた応答として扱う。入力を減らしてから続ける
pause_turnサーバ側の道具の途中応答をそのまま足して、送り直す

refusal は HTTP の 200 で返るので、エラーの率だけを見張っていると気づけません。止まった理由の内訳を、別の記録として見張ります（〈作って終わりではない〉）。

再試行の決まり

ゴール再試行を安全に組むための決まりを挙げられる。

決まり中身
間を延ばす間隔を少しずつ延ばして再試行する（指数バックオフ）。retry-after が付いていれば従う
重ねないSDK は既定で再試行する。その上に自前の再試行を重ねない（〈SDK は REST を包んでいる〉）
上限回数に上限を置き、超えたら人に知らせる
二重にしない副作用のある道具は、同じ要求が2回来ても一度しか実行しない形にしておく
記録応答ごとに付く request-id を記録し、追跡や問い合わせに使う
誤解「エラーが出たら、とりあえず同じ内容で何度か再試行すればよい」 実際は400 や 401 のように送った側の誤りは、何度送っても通らない。種類で分け、直すものは直す。
