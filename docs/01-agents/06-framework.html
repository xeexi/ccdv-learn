1-6　枠組みを使うか ─ Strands・LangGraph・PydanticAI

ゴールエージェントの枠組みを使う得と損を説明できる。

アプリ→Claude

エージェントを作るための枠組み（agentic abstraction frameworks）は、ループ・道具の定義・呼び出しのつなぎを肩代わりしてくれます。その代わり、中で何を送り、何が返っているかが見えにくくなります。

DOMAIN 1Agent Patterns and Frameworks

枠組み作り手特徴
StrandsAWS（オープンソース）進め方をモデルに任せる作りで、数行でエージェントが動く。既定のモデルの提供元は Amazon Bedrock で、Anthropic の API にもつなげる
LangGraphLangChain処理を、節点と辺のグラフとして組む。決まった手順と、モデルに任せる手順を1つのグラフに混ぜられる。状態を保存し、長い処理を途中から再開できる
PydanticAIPydantic のチームPython の枠組み。道具の引数や出力を型で決め、受け取った値を型で確かめる

ポイントどの枠組みも、中でしていることは同じループ。肩代わりするのは組み立ての手間で、何を送るか・どう書くかは変わらない。

得と損

ゴール枠組みを使うと楽になることと、困ることを挙げられる。

枠組みを使うと、始めるのが速くなります。モデルの呼び出し、道具の定義と解析、呼び出しのつなぎといった下回りを任せられ、状態の保存や再開、人の確認を挟む仕組みのような部品もそろっています。多くの枠組みは、使うモデルを差し替えられます。

その代わり、抽象の層が増えて、実際に送っているプロンプトと、返ってきた応答が見えにくくなります。うまく動かないときに原因を追いにくく、単純な作りで足りる仕事まで複雑に組みたくなります。公式は、中の動きを思い込みで使うことが、よくある失敗のもとだとしています。

選び方

ゴールAPI を直接使うか、枠組みを使うかを決められる。

公式の勧めは、まず API を直接使うことです。よくある型の多くは、数行のコードで書けます。枠組みを使うなら、中のコードを理解してから使います。本番に向けては、層を減らして基本の部品で組み直すこともためらいません。

Claude Code と同じ道具とループをそのまま使いたいなら〈Agent SDK で作る〉、ループの実行まで任せたいなら〈どこで動かすか〉へ進みます。

誤解「枠組みを使えば、プロンプトや道具の説明を考えなくてよい」 実際は枠組みが減らすのは組み立ての手間だけ。何を送り、道具をどう説明するかは、自分で決める。中が見えにくいぶん、確かめる手間はむしろ増える。
