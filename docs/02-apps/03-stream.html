2-3　逐次で受け取る ─ streaming

ゴール逐次で受け取ると何が変わり、途中で切れたらどう立て直すかを説明できる。

Claude→アプリ

逐次で受け取っても、全体にかかる時間とトークンは変わりません。変わるのは、最初の文字が早く届くことと、長い応答でも待ち時間の上限に掛かりにくいことです。届くのは断片なので、組み立てはアプリの側で行います（届く順は〈つなぎ方の違い〉）。

DOMAIN 2Claude API Mechanics

差分の種類何の断片か組み立て方
text_delta本文届いた順につなげる
input_json_delta道具の引数（JSON の文字列の切れ端）ブロックの終わり（content_block_stop）まで待ってから、JSON として読む
thinking_delta考えた内容つなげる。終わりの直前に、署名（signature_delta）が届く

ポイント断片は、ブロックの番号（index）ごとにつなげる。止まった理由は最後の message_delta で届くので、途中の断片を見て分岐しない。

組み立ては SDK に任せる

ゴール断片を自分で組み立てずに済む書き方を言える。

逐次で受けて、最後に1つにまとめる（Python）

with client.messages.stream(
        model=MODEL, max_tokens=8192,
        messages=msgs) as stream:
    for text in stream.text_stream:1
        print(text, end="")
    msg = stream.get_final_message()2
  1. 1本文の断片だけを、届いた順に受け取る。
  2. 2組み立て済みの応答を1つ受け取る。止まった理由と使用量も、ここで見る。

画面に出す必要がなくても、長い出力は逐次で受け、SDK に組み立てさせると安全です。SDK は、長くかかりそうな呼び出しを逐次にせずに送ろうとすると、送る前にエラーで止めます。

途中で切れたら

ゴール途中で切れた応答を立て直す手順を言える。

応答が流れ始めた後でも、エラーは届きます。混雑しているときは、途中で error イベント（overloaded_error など）が流れてくることがあり、ネットワークが切れることもあります。

手順中身
残すそれまでに受け取った分を保存する
頼み直す途中までの応答を示して「続きから書いて」と頼む、新しいリクエストを送る
限界道具の依頼と考えた内容のブロックは、途中からは立て直せない。最後の文章のブロックから続ける

イベントの種類は、今後増えることがあります。知らない種類は、読み飛ばすように書きます。

誤解「逐次で受け取れば、全体の時間も費用も減る」 実際は変わるのは、最初の文字が届くまでの時間。全体の時間とトークンは同じ。
