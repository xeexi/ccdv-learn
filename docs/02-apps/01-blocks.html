2-1　メッセージと content ブロック

ゴール1回の往復で送るもの・返るものを、ブロックの種類で説明できる。

アプリ→Claude→アプリ

API とのやり取りは、role と content を持つメッセージの列です。content の中身は種類（type）の付いたブロックの配列で、文章も画像も、道具の依頼も結果も、同じ配列に並びます。

DOMAIN 2Claude API Mechanics

道具を1回使う往復の、messages の中身

"messages": [
  { "role": "user", "content": [
    { "type": "image", "source": {…} },1
    { "type": "text",
      "text": "この請求書の合計は？" } ] },
  { "role": "assistant", "content": [
    { "type": "thinking", … },2
    { "type": "tool_use", "id": "toolu_01",
      "name": "calc", "input": {…} } ] },3
  { "role": "user", "content": [
    { "type": "tool_result",
      "tool_use_id": "toolu_01", … } ] }4
]
  1. 1画像もブロックの1つ。文より先に置くと、よく読まれる。
  2. 2考えた内容のブロック。返ってきたまま、手を加えずに履歴へ戻す。
  3. 3道具の依頼は、assistant の側に入る。
  4. 4道具の結果は、user の側に、同じ id を付けて入る。
ブロック書く側中身
textアプリ・Claude文章
imageアプリ画像（渡し方は〈データの渡し方と、呼び出し口〉）
documentアプリPDF や文書。出典を示させることもできる
tool_useClaude道具の名前・引数・呼び出しの id
tool_resultアプリ道具の結果。対応する id を付ける
thinkingClaude考えた内容（〈考えさせる量を選ぶ〉）

ポイント送るものも返るものも、type の付いたブロックの列。返ってきた content は、手を加えずにそのまま履歴に戻す。

画像を読ませる

ゴール画像を渡すときの形と、苦手なことを言える。

画像は image ブロックで渡します。形式は JPEG・PNG・GIF・WebP で、動く GIF は最初の1枚だけが使われます。画像も大きさに応じてトークンを使い、上限より大きい画像は縮めてから読まれます。細かい文字を読ませたいなら、送る前に切り抜くか、縮め方を自分で決めます。

苦手なこと中身
画質小さい・傾いた・ぼやけた画像は、読み違えやすい
数えるおおよその数になる。小さな物が多いと外れやすい
位置座標や位置はおおよそ。使う前に確かめる
人物画像の人物が誰かは答えない
生成画像AI が作った画像かどうかは、見分けられない

考えた内容のブロックと、道具

ゴール考えた内容のブロックを、道具の往復でどう扱うかを言える。

考えさせる設定のとき、応答には thinking ブロックが入ります。道具を使う往復を続けるときは、このブロックも含めて、返ってきた content をそのまま履歴に戻します。中身を書き換えたり一部だけを消したりすると、リクエストが拒まれることがあります。新しいモデルでは、ブロックそのものに手を加えなくても、それより前の履歴（system・ツールの定義・前のメッセージ）を書き換えるとブロックが無効になり、拒まれることがあります。履歴は後ろに足すだけにします。画面に表示するのは構いません。

誤解「履歴を軽くするため、考えた内容のブロックは消して送り直せばよい」 実際は道具の往復の途中では、手を加えずに戻すのが決まり。古い部分を減らしたいなら、刈り込みの機能を使う（〈窓を守る〉）。
