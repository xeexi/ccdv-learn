2-8　変更を管理する ─ バージョン管理・開発工程・レビュー

ゴールClaude が書いた変更を、バージョン管理と開発工程とレビューにどう載せるかを説明できる。

開発者→Claude Code→開発者

Claude が書いたコードも、人が書いたコードと同じ道を通します。ブランチで作り、テストで確かめ、プルリクエストでレビューを受けてから取り込む。この開発工程に Claude を組み込めば、速さを保ったまま、変更を追えて戻せる状態を保てます。

DOMAIN 2Software Engineering Foundations

ポイントClaude が書いた変更も、人の変更と同じ工程に載せる。取り込むかどうかは、テストとレビューで決める。

Claude を工程に組み込む

ゴール開発工程のどこで、どう Claude を動かせるかを挙げられる。

場所動かし方
GitHubプルリクエストや issue に @claude と書くと、Claude Code が GitHub Actions の中で動き、調べる・直す・プルリクエストを作る
CI の中CI の手順から、対話なしの実行（claude -p）で動かす。人が承認できないので、使える道具を先に決めておく（〈Claude Code の動かし方〉）
手元「プルリクエストを作って」と頼めば、コミットからプルリクエストまで進める

レビューする

ゴールClaude の変更をレビューするときの進め方を言える。

レビューは、書いた本人とは別の目で行います。Claude の変更なら、人が読むのに加えて、新しい文脈の Claude にもレビューさせます。書いたセッションは、自分が書いたコードに引きずられるからです（書く役とレビューする役を分ける形）。

「直しました」という言葉ではなく、テストの出力や、実行したコマンドとその結果のような証拠を見せさせます。証拠を見るほうが、自分で確かめ直すより速く確かです。Claude Code には手元の変更を調べるコマンド（/code-review・/security-review）があり、プルリクエストに自動でレビューのコメントを付ける機能もあります。自動のレビューは指摘を付けるだけで、承認や差し戻しはしません。

誤解「Claude が『テストは通りました』と言ったら、そのまま取り込んでよい」 実際は言葉ではなく証拠を見せさせ、CI でも確かめる。取り込む判断は人が行う。
