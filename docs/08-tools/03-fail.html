8-3　失敗の返し方と、承認の挟み方

ゴールツールの失敗を立て直せる形で返し、取り返しのつかない操作の前に承認を挟める。

アプリ→Claude

ツールは失敗します。握りつぶさず、Claude が次の手を選べる形で返します。

DOMAIN 8Tool Implementation

悪い返し方 ─ 何が起きたか分からない

{ "type": "tool_result",
  "tool_use_id": "toolu_01",
  "content": "error" }

よい返し方 ─ 失敗と、次の手が分かる

{ "type": "tool_result",
  "tool_use_id": "toolu_01",1
  "is_error": true,2
  "content": "注文 A-1O24 は見つからない。英字の O と数字の 0 の取り違えかもしれない。" }3
  1. 1結果は、対応する tool_use_id を付けて必ず返す。返さないと、次のリクエストがエラーになる。
  2. 2失敗したことを、is_error で示す。
  3. 3何が起きたかと、直す手がかりを書く。Claude はそれを読み、引数を直したり別の手に切り替えたりする。
失敗の種類返し方
入力の誤りどこがどう違うかと、正しい形を書く。直せば通る
一時的混雑や待ち時間切れは、ツールの中で間を空けて再試行する。それでも駄目なら、一時的な失敗だと書いて返す
直らない権限が無い、存在しない、など。再試行しても無駄だと分かるように書く

ポイント失敗は is_error と説明の文で返す。空の結果や「error」の一語では、Claude は次の手を選べない。

取り返しのつかない操作の前に、承認を挟む

ゴール承認を挟む位置と、断られたときの返し方を言える。

送信・削除・支払いのように取り返しのつかない操作は、実行の手前で人の承認を取ります。挟む場所はアプリの中で、tool_use を受けてから実行するまでの間です。断られたら実行せず、利用者が断ったことを結果に書いて返します。Claude はそれを読んで、別の進め方を考えます。

承認を挟みやすくするには、その操作を専用のツールとして切り出します。何でもできる bash の1行に紛れていると、アプリはどれが危ない操作かを見分けられません。send_email のような専用のツールなら、その呼び出しだけを止められます。

誤解「system プロンプトに、削除の前には必ず確認するよう書けば十分」 実際は頼むだけでは、確率的に破られることがある。アプリの側で、実行の手前に承認を挟んで止める。

※ Claude Code や Agent SDK では、承認の要否を権限の設定で決められます（〈Claude Code の動かし方〉）。フックで確実に止める形は〈壊す操作はフックで止める〉で扱います。
